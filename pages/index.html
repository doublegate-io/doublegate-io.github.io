    The problem

    What one session learns stays in that session

    The next session pays to learn it again, in model usage and in someone's time. A six-month field experiment across 66 firms found AI tools saved individuals time. The researchers detected no shift in the amount or mix of their tasks (AER: Insights). Sharing what agents learn is a separate change, and its effect on a business is unmeasured.

    A correction waits for a reviewer
    A correction becomes a claim, held where it was learned until a person or grading model other than its author signs it. That review costs someone's time, model usage, or both.
    A rejection keeps its reasons
    A rejected claim, or a demoted one taken out of recall, keeps its content and the reasons for the decision. Nothing is deleted, so storage only grows.

    The example, opened up

    Revision 4 of the alert policy, held and rejected

    The example is illustrative: one team's alert policy for its payments sandbox. Revision 3, the source of the map's selected claim, requires an owner team, a runbook link and a severity on every alert.

    Revision 4 adds a rollback test and is held. The grading model's two readings disagree, so it waits for a person, who rejects it: the test it cites is missing. Revision 3 stays promoted. A promotion never carries over to the next revision.

    Nothing is shared knowledge until a reviewer other than its author has signed it.

    How to check it

    Five rules the gate enforces, and how to check each

    Rule 1

    The reviewer is never the author.

    The gate never counts a signature from the identity that wrote a claim: an agent, a person or the operator. The console shows its author Refused: the claim's author cannot sign it in place of Sign. An agent-role API key reaches {agent_reach} published methods. None of them promotes, signs, rejects, demotes or hides, and no method deletes. If an agent starts as the gate's own operating-system user, its shell can promote what its session wrote (how to prevent that). Run the agent as another operating-system user and the rule holds against it. A gate that runs under a service user of its own is on the roadmap.

    How to check it
    Rule 2

    Other agents can find a claim once it is signed.

    Recall returns promoted claims and the asker's own held ones, marked as held, never another author's held claim. By default one grading model reads each claim twice, once for it and once against, and those two readings can promote it with no person.

    How to check it
    Rule 3

    Every decision is signed and kept.

    The journal records every claim written, promoted, rejected or demoted as a signed event. Each entry links to the one before, so a later change shows. One command checks every signature. How fast storage grows is measured on the evidence page.

    How to check it
    Rule 4

    Only its author and reviewers can read a held claim.

    Without the reviewer role, a caller asking for another author's held claim, by id, listing or count, is answered as if it did not exist. We publish the four things it can still learn. Three are that the quarantine is full, that it is more than 1,000 events behind, and roughly how long the journal is. The fourth takes many timed calls: whether a claim exists whose id it holds or can compute. An id is a digest of the whole write. What a caller can still learn, measured →

    How to check it
    Rule 5

    Promotion makes a claim findable and never ranks it higher.

    Promotion decides whether recall can return a claim, and adds no weight to its order. Neither does the provisional mark. By default recall matches words. Matching by meaning needs an embedding model the operator configures.
