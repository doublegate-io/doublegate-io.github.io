For engineers

It replaces your memory provider.
Your read path does not change.

doublegate speaks the interface your agent already speaks for storing and searching what it learns. Swapping to it changes one thing: what gets in. Everything below is what that costs, how it plugs in, and when each release lands.

Where it sits

Not a proxy in front of a provider. It is the provider.

LayerResponsible forDecides whether content is trustworthy?
Your agent Hermes · Claude Code · opencode · Codex doing the work, calling tools no
Today's memory tools mem0 · Zep · Letta · Mnemosyne storing and ranking what it learns ranks it — never blocks it
doublegate storing, searching, and checking on the way in yes

Sitting in front of an existing provider was considered and rejected — you cannot enforce a read boundary you do not own. That is a deliberate decision, not an oversight.

What it stores

One store, several kinds of artifact, all on the same write path. A skill is not special-cased — it is content with a different shape and a scanner that knows about executables.

ArtifactWhat it isReviewed?
Memories claims your agent will act on as true yes — held until signed
Skills installable capability, including whatever it can execute yes — scanned for payloads, then graded
Connector output beliefs proposed by an existing system yes — same path, scoped by contract
Verdicts the record of who approved or refused what, and why not reviewed — it is the review
Records transcripts, tool output, logs no — they report events, they do not claim truth

Every artifact above is audited, traceable, versioned and discoverable — the same four properties, because they share one write path and one journal. Nothing is edited in place: a correction is a new version linked to what it replaced, so an artifact you depend on cannot quietly become something else.

What it costs

Three real costs, each with its number.

⊘

Read latency: unchanged

The gate is not in the query path at all. Approved content sits in an ordinary store and is searched normally — no reviewer call, no per-query check, no extra round trip.

reads never touch the gate

◫

Write latency: under 50 ms

Writes are fire-and-forget — your agent enqueues and continues. Review happens in a background loop, so a slow reviewer never blocks the agent that wrote the content.

budget for the synchronous path

⎔

Tokens: about 5% of an agent day

Grading calls a model. On a real 393-memory corpus with two reviewers per claim, that came to roughly five percent of the agent's own daily spend — reported per gate, never hidden, and the local models take the cheap cases first.

measured on our corpus

Only claims are reviewed. Transcripts, tool output and logs pass straight through as records. On our machines an agent produced roughly ninety times more records than claims, so the fraction actually reaching a model is small — but that ratio is from our machines, not a population finding, and yours will differ.

What plugging it in actually looks like

Your agent does not learn a new protocol. doublegate speaks the standard agent-tool protocol already built into Hermes, Claude Code, opencode and Codex — add it like any other tool server and the agent gains its four everyday tools — no adapter code, no SDK to install. A fifth and sixth exist for review queues and the organization side; the everyday surface is the four below.

remember

Your agent writes something down. It gets back an artifact id and a state — the content exists but is not readable by anyone until review finishes. Submission returns immediately; grading happens after.

recall

Search the approved store. Every result carries its provenance — who signed it, on what basis, when. The read path is an ordinary search, so it stays fast and cheap.

why

The audit answer for any one thing in the store: every event that moved it, in order, with signatures. “Audited” stops being a word on a slide and becomes a query your agent or your compliance team can run.

gaps

What this folder is still missing: topics its queries keep failing to find, and what connected folders already hold. The agent asks; the system proposes which reviewed items would fill the hole; a person acts on it.

one memory, end to end
// your agent writes down a correction it was just taught
> remember "Payments sandbox rate-limits per API key, not per account.
             Space retries 2 s apart, not 30."
← artifact sha256:9f2c… · state: held — stored, not yet readable by anyone else
  scan: clean · near-duplicate found: an older team note — this one sharpens it

// minutes later, after a reviewer that did not write it signs off
> recall "sandbox rate limit"
← "…per API key, not per account. Space retries 2 s…"
  signed: reviewer-2 · 09:16 · source: the session it was taught in · provisional: no

// the audit answer, for any artifact, at any time
> why sha256:9f2c…
← admitted 09:14 → scanned, no findings → graded 0.91 by reviewer-2, not the author
  → signed 09:16 → readable to your group · every step signed; the chain verifies end to end

A fifth tool reports what is waiting in review — ids and states only, never the content itself, so even the queue view respects the boundary. On the organization side a sixth, submit, is the only way in: content reaches the company gate solely from a client gate that already admitted it. No tool anywhere in the surface can change a verdict, set a trust class, or promote its own output.

Python, SQLite, one crypto library

The core is standard library plus SQLite plus a signing library. No vector database to operate, no message broker, no container orchestration. It runs as a sidecar on the machine that already runs your agent, and grading goes through whatever inference you already pay for — there is no doublegate service in the path.

A deliberate dependency budget, recorded as a design decision

Review keeps running offline

Checking does not need paid inference: the small local models run on your CPU with no key and no quota, so grading works with the network down. When a second gate sits above yours and cannot be reached, the items it has not confirmed carry a provisional mark — visible everywhere the content appears — until its verdict lands on reconnect.

Offline is a working state, not a degraded one

Content stays where you put it

Everything — the review store, the approved store, the event record — runs on your hardware. Sharing outward is opt-in per folder, never a default, and a deployment with no outgoing connections is a complete, working one.

Content stays on your machine by default; sharing is opt-in per scope

Two things to know before you wire it in

Both are on the roadmap with a release attached. Until they land, they change how you would wire it in, so they are stated here rather than discovered later.

  • One gate is one trust domain until read scopes ship. Admission is governed from the first release; who may read what, by identity and team, arrives in release 4. Before that, put knowledge with different audiences behind different gates — the folder model already keeps them apart.
  • Deletion is cryptographic, and it ships with the multi-machine release. Decisions stay signed and permanent; the content they refer to does not. Erasing a subject destroys the keys that unlock their content and records that as an event — the audit trail stays verifiable after the erasure, and nothing disappears silently. The schema carries the keys from release 1; the erasure tooling lands in release 4.

Every item on this page is tracked in the public roadmap with an owner, a target release and the test that closes it.

When you can run it

Five releases, each one usable on its own. The first release you can point an agent at is the second one — that is the one to plan around.

  1. R1Ledger and quarantine, no model in the loop Append-only signed journal, two-store isolation, the frozen envelope format. The part every later release depends on, and the part with no unknowns.
  2. R2A memory provider you can point an agent at — Q2 2027 The adoption release. Its own store, hybrid search, the standard agent-tool interface, an importer from what you run today, and the first client. Replaces your provider; checking follows.
  3. R3The gate itself Scanner, independent grading, signed verdicts, the local preparation models. A published catch rate against a poisoning benchmark is the exit test.
  4. R4Multi-machine, the organization gate, read scopes, erasure Journal sync, provisional promotion while a gate is unreachable, the second authority, read permissions by identity and team, the erasure tooling.
  5. R5Daily-driver review loop The digest capped at ten items a day, demotion on contradiction, skill revision proposals, a zero-config default profile.

Release 2 is dated because it is being built; later releases are dated when their predecessor ships, and every date on this site comes from the same public roadmap.
