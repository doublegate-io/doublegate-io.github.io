For engineers

It replaces your memory provider.
Review on write. Eligibility on read.

doublegate speaks the interface your agent already speaks for storing and searching what it learns. It controls what gets in and which approved knowledge a caller can use. Everything below is what that costs, how it plugs in, and when each release lands.

Where it sits#

A memory provider that owns admission, storage and eligible retrieval.

LayerResponsible forRole in review
Your agent Hermes · Claude Code · opencode · Codex doing the work, calling tools no
Storage and search storing and ranking what it learns retrieval and ranking
doublegate storing, searching, and checking on the way in scoped admission decisions

The provider owns both the review boundary and the retrieval boundary. The agent performs the work; the gate maintains the knowledge it is authorized to use.

What it stores#

One store, several kinds of artifact, all on the same write path. A skill is not special-cased — it is content with a different shape and a scanner that knows about executables.

ArtifactWhat it isReviewed?
Memories claims your agent will act on as true yes — held until signed
Skills installable capability, including whatever it can execute yes — scanned for payloads, then graded
Connector output beliefs proposed by an existing system yes — same path, scoped by contract
Verdicts the record of who approved or refused what, and why not reviewed — it is the review
Records transcripts, tool output, logs no — they report events, they do not claim truth

The target is for every artifact above to be audited, traceable, versioned and discoverable — the same four properties, because they share one write path and one journal. Nothing is edited in place: a correction is a new version linked to what it replaced, so an artifact you depend on cannot quietly become something else. Skills and skill-revision proposals are allocated to release 5.

What it costs#

Budget for retrieval, time to publication and reviewing inference.

⊘

Retrieval: eligibility before ranking

Model review runs before publication. Reads enforce current access, scope, expiry and authority before ranking eligible knowledge. Measure that cost on your workload.

review and read authorization are separate.

◫

Write-path target: under 50 ms

The write includes the initial security scan. Model grading and subsequent review run in the background. The latency target applies to that initial write path, not the time to shared publication.

budget for the synchronous path

⎔

Tokens: about 5% of an agent day

A historical 393-memory experiment with two reviewers per claim used roughly five percent of the agent's daily token spend. Re-measure the selected two-stage workflow with your models, evidence sizes, retries and optional human review.

measured on our corpus

Only claims are reviewed. Transcripts, tool output and logs pass straight through as records. On our machines an agent produced roughly ninety times more records than claims, so the fraction actually reaching a model is small — but that ratio is from our machines, not a population finding, and yours will differ.

What plugging it in actually looks like#

Your agent does not learn a new protocol. doublegate speaks the standard agent-tool protocol already built into Hermes, Claude Code, opencode and Codex — add it like any other tool server. The examples below cover everyday use; the published tool catalog specifies the surface exposed by each deployment tier in the current development API. The release-3 design below adds the selected two-stage review and planned writer preview; the catalog remains the contract for current integration. Gap proposals are planned for release 4.

remember

Your agent submits a contribution and receives its identifier and state. The write waits for the security scan; grading follows in the background. The planned writer preview marks a scan-cleared contribution as pending review; that preview does not grant shared admission.

recall

Search admitted knowledge with its provenance: who signed it, on what basis and when. The proposed writer-preview path would expose the caller's own scan-cleared contributions separately from admitted consumer results, explicitly marked as pending review.

why

The audit answer for any one thing in the store: every event that moved it, in order, with signatures. “Audited” stops being a word on a slide and becomes a query your agent or your compliance team can run.

gaps

What this folder is still missing: topics its queries keep failing to find, and what connected folders already hold. The agent asks; the system proposes which reviewed items would fill the hole; a person acts on it.

> why sha256:9f2c…
← admitted 09:14 → scanned, no findings → trust 91/100 by reviewer-1, not the author
  → APPROVE by reviewer-2 for this version and use → published to authorized readers · every step signed; the chain verifies end to end

Queue inspection returns identifiers and states rather than quarantined content. Organization submissions come from an authorized client gate with proof of local admission. The published API separates agent-facing operations from operator controls.

Local storage; organization authority

The client uses Python and local SQLite storage. The organization design uses PostgreSQL for authoritative decisions and Delta for rebuildable projections. Storage, reviewing inference and operations have separate budgets; size them from measured workloads.

A deliberate dependency budget, recorded as a design decision

Fully local review with local judges

Use locally hosted reviewing models for offline grading. Small preparation models supply advisory signals; the reviewing models issue verdicts. Size the hardware for the judges your policy requires. If those backends are unavailable, the gate keeps serving admitted knowledge while new contributions wait for review.

Local storage and local inference are separate deployment choices

Content stays where you put it

The review store, approved store and decision record run on your hardware. Hosted reviewing models receive the content they evaluate; locally hosted models keep that inference on your infrastructure. Sharing between gates is configured per folder.

Choose storage, inference and distribution boundaries explicitly

Deployment and operating controls#

Inter-deployment traffic uses authenticated HTTP only. Local tool and socket adapters stay inside their deployment; they do not become synchronization channels.

The organization release separates contributor identity, team membership, ownership and read grants. Credentials carry explicit scopes; rotation and revocation must preserve historical signature verification. Source acquisition runs outside the reviewing gate, with bounded network access and submission credentials rather than approval keys.

Plan private storage, reviewing inference, backups, restore drills and operational monitoring together. Queue age, review failures, policy refusals and synchronization lag show where work is waiting. Tenant isolation and recovery are deployment acceptance tests.

The release sequence below allocates these controls. Evaluate the installed service against its published API and acceptance evidence before opening a shared pilot.

For the agent doing the wiring#

The whole surface is published as data, rendered from the code that serves it and checked against that code before it ships. An agent asked to build tooling against a gate reads four files and a short index; a running gate answers the same documents when asked.

All four live under /api/ on this domain, and the index at /llms.txt is what a program reads first: the product in one paragraph, the four documents, and the rules agents most often get wrong from tool names alone — a handle is not admission, identity is never a parameter, nothing in the surface promotes. A manifest beside them names the commit each document was rendered from.

Two things to know before you wire it in#

Access grants and content erasure are separate controls. Plan each explicitly when connecting collections with different audiences or retention requirements.

  • Organization-gate read access is granted by key and folder. Issue revocable keys with explicit read grants to named folders. Folder-scoped search selects content; the key's grants authorize access. Treat local keyless operation as a single-operator trust domain.
  • Deletion is cryptographic, and it ships with the multi-machine release. Decisions stay signed and permanent; the content they refer to does not. Erasing a subject destroys the keys that unlock their content and records that as an event — the audit trail stays verifiable after the erasure, and nothing disappears silently. The schema carries the keys from release 1; the erasure tooling lands in release 4.

Measure useful reuse and review quality#

Release 3 evaluates harmful admissions, useful contributions rejected, review latency and cost per useful admission on a held-out corpus. Reviewer provenance records shared models and evidence; joint failures measure how much a second review adds.

Release 4 adds a two-deployment trial: current-access checks, withdrawal propagation, failure recovery and cross-team reuse. Compare the same tasks and review budget with conventional storage and workflow. Record opportunities to reuse knowledge, actual reuse, and the cost of maintaining it before estimating savings.

Benchmark targets are acceptance criteria. Measured results need a corpus, denominator and uncertainty before they become deployment or business claims.

When you can run it#

Five releases, each one usable on its own. The first release you can point an agent at is the second one — that is the one to plan around.

  1. R1Ledger and quarantine, no model in the loop Append-only signed journal, two-store isolation, the signed envelope format. Integrity and replay checks establish the foundation for later releases.
  2. R2A memory provider you can point an agent at — Q2 2027 The adoption release. Its own store, hybrid search, the standard agent-tool interface, an importer from what you run today, and the first client. Replaces your provider; checking follows.
  3. R3The gate itself Scanner, an AI trust assessment from 0–100, then a distinct authorized AI or human approving or rejecting the exact revision and use. Evidence and signed decisions travel together. Calibration, false acceptances and false rejections are release tests.
  4. R4Multi-machine, the organization gate, read scopes, erasure Authenticated HTTP synchronization, organization authority, required verified contributor and team attribution, current read permissions, scoped publication and withdrawal, and erasure tooling. Team moves retain original attribution; ownership transfers are recorded.
  5. R5Daily-driver review loop The digest capped at ten items a day, demotion on contradiction, skill revision proposals, a zero-config default profile.

Release 2 is dated because it is being built; later releases are dated when their predecessor ships, and every date on this site comes from the same public roadmap.
